\section{Objectif}
L'objectif du laboratoire est de développer un driver Linux permettant d'interfacer
notre IP AXI4-Lite avec une application user-space.
Le driver doit offrir une interface simple d'utilisation depuis Linux, tout en
vérifiant à l'initialisation que le design chargé dans le FPGA est correct.

\section{Interface mise en place}
L'interface choisie est un \textbf{driver caractère} exposé via le noeud
\texttt{/dev/axi\_lw}.
Le module est chargé avec \texttt{insmod}, puis l'application user-space ouvre
ce device et communique avec le kernel par \texttt{ioctl}.

Le driver utilise un \texttt{miscdevice} afin de réduire le code de création
du périphérique (pas de \texttt{cdev/class/device} manuel).

\subsection*{Justification du choix}
J'ai choisi un driver caractère chargé manuellement, en cohérence avec ce qui a
été vu dans le cours de drivers Linux et pour garder une mise en oeuvre simple
dans le cadre du laboratoire.
Une alternative aurait été un driver auto-chargé (\textit{platform driver}),
mais cette approche demandait d'adapter le Device Tree.
Pour ce laboratoire, l'effort supplémentaire côté Device Tree n'était pas
nécessaire.
Le compromis retenu est donc d'utiliser \texttt{insmod} à chaque itération de
test, ce qui restait acceptable par rapport à la complexité d'une adaptation DT.

\subsection*{Accès matériel}
Le module mappe la zone AXI lightweight à l'adresse \texttt{0xFF200000}
(\texttt{ioremap}).
Au chargement, il lit le registre constant (\texttt{REG\_CST}) et compare avec
\texttt{0xBADB100D}. Si la valeur ne correspond pas, le module retourne
\texttt{-ENODEV} et refuse de s'initialiser.

\newpage

\subsection*{API ioctl utilisée}
Les commandes \texttt{ioctl} retenues pour l'application de test sont:
\begin{itemize}
    \item lecture: \texttt{GET\_CST}, \texttt{GET\_TEST}, \texttt{GET\_SWITCH}, \texttt{GET\_KEYS\_EDGE}
    \item écriture: \texttt{SET\_TEST}, \texttt{SET\_LEDS}, \texttt{CLR\_LEDS}, \texttt{SET\_HEX3\_0}, \texttt{SET\_HEX5\_4}
\end{itemize}

Le choix de \texttt{GET\_KEYS\_EDGE} (avec acquittement automatique) permet un
comportement événementiel: une action par appui de touche, sans répétition
continue pendant un appui long.

\section{Application user-space}
L'application \texttt{axi\_ctl.c} a été adaptée pour reprendre la logique du
labo 6:
\begin{itemize}
    \item lecture et vérification de la constante
    \item écriture/lecture du registre de test
    \item boucle principale avec gestion des touches KEY0..KEY3
    \item affichage de la valeur sur les 7 segments et gestion des LEDs
\end{itemize}

La différence principale est que l'accès matériel direct (\texttt{/dev/mem})
est remplacé par l'interface du driver.

\section{Validation}
Les tests effectués:
\begin{itemize}
    \item compilation du module (\texttt{axi\_driver.ko})
    \item chargement avec \texttt{insmod} et création de \texttt{/dev/axi\_lw}
    \item exécution de l'application user-space et vérification du comportement
\end{itemize}

Le module se charge correctement et l'application permet de piloter les
registres de l'IP via \texttt{ioctl}.
